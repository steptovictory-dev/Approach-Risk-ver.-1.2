# SQL JOIN – как наблюдение получает split

В `examples` одна строка представляет пару наблюдений одного захода. В `study_days` одна строка представляет день исследования для аэропорта. Тысячи наблюдений одного дня используют одну запись с season и split

```sql
SELECT e.event_id, e.origin_time, d.season, d.split
FROM altitude.examples e
JOIN altitude.study_days d USING (airport, day);
```

`e` и `d` – короткие имена таблиц. `USING (airport, day)` требует совпадения обоих полей. Оно соответствует условию `ON e.airport = d.airport AND e.day = d.day`. Аэропорт нужен, потому что одна календарная дата может существовать сразу в LFPG, EGLL и EDDF

Соединение имеет отношение многие к одному: много наблюдений получают одну запись дня. PRIMARY KEY (airport, day) запрещает два соответствующих дня; FOREIGN KEY в examples запрещает отсутствие дня. Поэтому каждая исходная строка получает ровно одну метку split

| Split | Пар наблюдений | Заходов | Дней |
| --- | ---: | ---: | ---: |
| Train | 10 715 | 384 | 9 |
| Validation | 3 292 | 114 | 3 |
| Test | 1 924 | 55 | 3 |

INNER JOIN возвращает только совпадения. Без внешнего ключа отсутствие записи дня могло бы незаметно удалить наблюдения из результата. Для диагностики применяется LEFT JOIN: он сохраняет наблюдения без совпадения и позволяет найти их через `d.airport IS NULL`

Одинакового числа строк до и после соединения недостаточно: потеря одной строки и размножение другой могли бы компенсировать друг друга. Поэтому проверяем отсутствие пропусков и единственность соответствия каждого ключа отдельно
